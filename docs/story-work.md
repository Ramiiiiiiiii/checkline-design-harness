# 체크라인 — 디자인 작업 흐름 (AI 없이 손으로 한 방식)

> 이 문서는 "내가 실제로 어떻게 작업했는지"의 기록입니다.
> "무엇을 위한 일인지"는 `story-service.md`를 참고하세요. 둘은 섞지 않습니다.
> 실무에서 하던 방식을 회사·고객 이름 없이 옮겼습니다.

## 작업 흐름

| 단계 | 누가 | 한 일                                         | 산출물                                              | 게이트                                       | 넘김                        |
| ---- | ---- | --------------------------------------------- | --------------------------------------------------- | -------------------------------------------- | --------------------------- |
| ①    | 나   | AS-IS 화면과 지적된 문제점 목록 확인          | AS-IS 화면 캡처 + 문제점 목록                       |                                              | 클라이언트·팀 → 나 (사람)   |
| ②    | 나   | AS-IS를 UI/UX 관점에서 분석, 개선 방향 결정   | UI/UX 진단 문서(정보 구조·작업 흐름·사용 환경·시각 위계) | ✅ 무엇을 고칠지 내가 판단 (내부)            |                             |
| ③    | 나   | 레퍼런스·무드보드 수집, 방향 시안 제작        | 방향 시안 2~3개 + 시안별 "해결한 문제" 설명         |                                              | 나 → Figma (도구)           |
| ④    | 나   | 시안과 해결한 문제를 함께 보여주고 방향 확정  | 확정 시안                                           | ✅ 클라이언트 컨펌 (반려 시 ③으로)           | 나 → 클라이언트 (사람)      |
| ⑤    | 나   | 개발 CSS 기준 토큰·컴포넌트 제작, TO-BE 조립  | 디자인 토큰, 컴포넌트, TO-BE 화면                   |                                              | 개발 CSS → 나, 나 → Figma (도구) |
| ⑥    | 나   | 웹 화면을 모바일·태블릿으로 변환             | 모바일(360×740)·태블릿(1280×800) 화면 + 추가 모바일 컴포넌트 |                                    | Figma (도구)                |
| ⑦    | 나   | QA 체크리스트로 위반 검토 후 전달             | QA 결과 + 퍼블리싱용 최종 화면                      | ✅ 토큰·컴포넌트 규칙 위반 여부 (기준 문서)  | 나 → 퍼블리셔 (사람)        |

## 원문 (작업자 진술)

1. 나는 기존 화면(AS-IS)과 클라이언트·팀이 지적한 문제점 목록을 받아 확인한다.
2. AS-IS를 UI/UX 관점에서 분석한다. 정보 구조, 작업 흐름, 사용 환경(현장 터치 단말·저해상도 모니터), 시각 위계를 보고 문제점을 진단해 개선 방향을 정한다.
3. 레퍼런스와 무드보드를 모아 방향 시안 2~3개를 Figma에 만들고, 시안마다 어떤 문제를 해결했는지 적는다.
4. 클라이언트에게 시안과 해결한 문제를 함께 보여주고 방향을 확정받는다. 반려되면 3으로 돌아간다.
5. 확정된 방향에 맞춰 실제 개발 CSS 값 기준으로 토큰과 컴포넌트를 만들고(확정 안 된 값은 "임의값" 표시), 오토레이아웃으로 TO-BE 화면을 조립한다.
6. 웹 화면을 구조는 유지한 채 모바일(360×740)·태블릿(1280×800)으로 변환하고, 부족한 모바일 컴포넌트를 추가한다.
7. QA 체크리스트로 컴포넌트·토큰 위반 여부를 검토한 뒤 퍼블리셔에게 넘긴다.

## 작업자 메모 — 왜 ② 뒤에 외부 게이트가 없는가

- 분석 결과만 따로 공유하면 클라이언트는 그게 문제인지 모르는 경우가 많다. 문제는 시안을 **봐야** 알게 된다.
- 그래서 문제 정의는 따로 컨펌받지 않고, ③ 시안에 "해결한 문제"를 붙여 ④에서 함께 확인받는다.
- 시안에서 추가로 해결한 문제를 보고 클라이언트가 좋아하는 경우도 있다. ②의 진단은 ④ 컨펌 자료의 근거가 된다.
