# P1 진단 — 관리자 설비 현황 대시보드

> AS-IS: 종이 점검표 + 엑셀 취합 + 메신저 수리 요청 (defaults.yaml p1.as_is, prd.md §1)
> 기준 문서: docs/prd.md, docs/story-service.md, docs/story-work.md
> 전제: 클라이언트(공장)는 지금 무엇이 문제인지 모른다. 문제는 화면을 보고서야 드러난다 (r2-purpose.md).

## AS-IS 문제점

### D1. 공장 전체 상태를 한 번에 볼 수 있는 곳이 없다
- 관점: 정보 구조
- 근거: 점검 결과는 설비 옆 종이에, 이상 보고는 메신저에, 취합본은 엑셀에 흩어져 있다 (PRD §1). 세 곳을 모두 열어야 "지금 공장 상태"를 알 수 있다.
- 영향: 관리자 — 아침 회의 전에 현황을 말할 수 없고, 하루가 끝나야 전체 그림을 본다.

### D2. 이상이 생겨도 관리자에게 늦게 도착한다
- 관점: 작업 흐름
- 근거: 종이를 걷어 엑셀에 옮기는 일이 하루 끝에 몰린다 (PRD §1). 메신저 사진은 다른 대화에 밀린다.
- 영향: 관리자 — 이상 보고 → 수리 배정이 몇 시간 늦어진다 (PRD §9 목표: 30분 이내).

### D3. 가동 정지 설비와 정상 설비가 기록에서 똑같아 보인다
- 관점: 시각 위계
- 근거: 종이 점검표와 엑셀은 모든 행이 같은 모양이다. "즉시 정지"는 체크 표시 하나로만 구분된다. story-service ★1은 정지 설비가 어디서도 정상처럼 보이면 안 된다고 정한다 (PRD §8-1).
- 영향: 현장 작업자 — 정지 설비를 모르고 돌릴 위험. 관리자 — 위험한 것부터 처리할 수 없다.

### D4. 누가 아직 점검하지 않았는지 알 수 없다
- 관점: 정보 구조
- 근거: 빈 칸은 "안 했다"인지 "해당 없음"인지 구분되지 않는다. 미점검 설비 목록이 따로 없다 (PRD §3-2).
- 영향: 관리자 — 일일 점검 완료율(PRD §9 목표 95%)을 측정할 수 없다.

### D5. 수리가 지금 어디까지 왔는지 추적할 수 없다
- 관점: 작업 흐름
- 근거: 수리 요청과 완료가 메신저 대화로만 오간다. 접수 → 배정 → 수리 중 → 완료 → 재가동 확인 단계가 기록되지 않는다 (PRD §6-5, §6-6).
- 영향: 관리자·수리 담당자 — 같은 설비를 두 번 배정하거나, 재가동 확인 없이 정지 표시가 사라진다.

### D6. 관리자 PC 환경을 고려한 정보 밀도가 아니다
- 관점: 사용 환경
- 근거: 엑셀은 열이 많아 가로 스크롤이 생기고, 일부 저해상도 모니터에서 핵심 열이 화면 밖으로 밀린다 (PRD §4 사용자 환경).
- 영향: 관리자 — 여러 라인을 동시에 보면서 상태 열을 놓친다.

## 대시보드가 드러내야 할 것

- D1 → 한 화면 상단에 상태별 개수(정상·이상·가동 정지·미점검·수리 중) 요약
- D2·D3 → 가동 정지와 이상 보고를 **가장 먼저** 보이는 위치에, 아이콘 + 텍스트로
- D4 → 미점검 설비 목록과 담당자, 알림 보내기 액션 (PRD §6-4)
- D5 → 수리 진행 단계(접수·배정·수리 중·수리 완료·재가동 확인)를 한 줄로
- D6 → 1920 기준에서 가로 스크롤 없는 표, 상태 열은 왼쪽 고정
