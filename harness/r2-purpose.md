# R2 — 목적

> 인터뷰 라운드 R2 확정본. 근거: 사용자 답변(2026-10-10), `docs/story-service.md`, `docs/story-work.md`, `docs/prd.md` §1·§6-4

## 한 문장 목적

> 체크라인 화면을 만들 때 **AI가 기획·요소를 몰래 추가하거나 디자인 규칙을 어기지 못하게** 막고, 개선안 시안 3개 → 선택 → 웹·태블릿·모바일(라이트/다크) 완성까지 같은 품질로 반복되게 한다.

## 무엇이 매번 달라지나 (막고 싶은 것)

| # | 문제 | 하네스의 대응 |
| --- | --- | --- |
| 1 | AI가 PRD·story에 없는 기획이나 요소를 마음대로 추가하고 **표시하지 않는다** | 추가 요소는 `[추가 제안]` 표기 + 근거 필수. 표기 없는 추가는 게이트 실패 (design.md 5-2 ⑧) |
| 2 | 매번 화면 규칙·디자인 규칙(원티드 DS)에 어긋난 결과를 만든다 | 색·타이포·간격·모서리·컴포넌트를 `rules.yaml` 허용 목록으로 기계 판정 (design.md 5-2 ③④⑥) |
| 3 | 다크 모드를 빠뜨리거나 HEX를 하드코딩해 다크에서 깨진다 | Light·Dark 쌍 + 변수 바인딩 100% 판정 (design.md 5-2 ⑦) |

## 사용자

| 누구 | 역할 |
| --- | --- |
| 나 (프로덕트 디자이너) | 하네스를 실행하고, 시안을 고르고, 승인한다 |
| 퍼블리셔 | 결과물(최종 Figma 화면)만 받는다. 하네스를 실행하지 않는다 |
| 클라이언트 | 시안 3개 중 방향을 함께 고른다 (story-work ④) |

## 실행 단위 (하네스 한 번 = 무엇)

- **화면 주제 1개**에 대해:
  1. 개선안 **시안 3개**를 만든다 (각 시안에 "해결한 문제" 표기)
  2. 내가(또는 클라이언트와) **1개를 선택**한다
  3. 선택안으로 **웹(1920) · 태블릿(1280×800) · 모바일(360×740)** 을 **라이트·다크 모두** 만든다 → 화면 6장 이상

## 이번 실행의 AS-IS와 최종 결과물

- **AS-IS**: 종이 점검표 + 엑셀 취합 + 메신저 수리 요청 (PRD §1 배경)
- **현실 조건**: 클라이언트(공장)는 지금 무엇이 문제인지 모른다. 문제는 시안을 보고서야 알게 된다 (story-work 작업자 메모).
- **최종 결과물**: 현재 **문제 상황과 현황을 한눈에 알리는 관리자 대시보드** (PRD §3-2, §6-4)
  - 오늘 점검 현황, 미점검 설비, 이상 보고, **가동 정지 설비**, 수리 진행 상태가 한 화면에서 보여야 한다.
  - 각 시안은 "종이·엑셀 방식에서 보이지 않던 문제를 이 화면이 어떻게 드러내는지"를 함께 적는다.

## 완료 기준 (한 문장)

> 선택된 시안으로 만든 대시보드 화면이 웹·태블릿·모바일 × 라이트·다크 **6장 모두** 게이트(DS 규칙·서비스 규칙·추가 요소 표기)를 통과하고, 내가 최종 승인하면 완료다.
